Assertion-by-assertion assessment

A01: Correct. Public Event.build constructs an S actor / S key-label ACK that
references O's genuine SEND. receive accepts and applies it although S has no
local receipt or ACK witness. The test observes S before and after and checks
both the O effect and its result code.

A02: Correct. Lambda queues the same unsigned ACK twice. Its deliveries call
the same receive method; the first applies and the second is a duplicate because
the event ID is already in O's local effect IDs. Three O RAW entries are expected:
one SEND and two deliveries. Deduplication is not authenticated replay defense.

A03: Correct. The existing verifier accepts the consistent O hash-linked ledger
that contains the forged ACK. Its checks concern record numbering, links, hashes,
and adjacent view continuity. It does not prove peer authorship or independently
re-execute all transition semantics. The PR appropriately limits this claim.

A04: Correct and useful. Changing key_id to O while retaining actor S, then
rehashing the complete public event body, isolates ACTOR_KEY_MISMATCH from
EVENT_HASH_MISMATCH. The original acceptance test did not isolate these checks
because it changed the key without recomputing the event hash.

A05: Correct. An internally consistent ACK with an unknown SEND reference is
rejected as ACK_REFERENCE_NOT_LOCAL_SEND. This prevents the conclusion from
being overstated as acceptance of arbitrary ACK references.

A06: Correct. Calling S.acknowledge without S having received the SEND is
rejected as REFERENCED_SEND_NOT_RECEIVED. This local API restriction does not
protect O's independently reachable inbound receive method.

A07: Correct positive control. S actually receives the SEND and acknowledges it;
O accepts. The local S ACK witness is present. Dataclass equality with the public
builder output establishes identical event fields and hence identical canonical
event serialization; that event ID does not distinguish the two origins.

Correction 2: retain failure evidence after unexpected runner errors

Location: extensions/c6_sender_authentication/run_review.py lines 64-108,
especially the probe and trace work at lines 83-95.

There is no exception-safe finalization. With a process-local simulated OSError
from reference_trace.write_reference_trace, both suites passed and their logs
were written, but the process exited 1 before baseline_after or execution_receipt
was written. This is a reporting omission, not a false successful status.

Exact correction: initialize a failed/in-progress receipt before loading the
manifest; run manifest loading, tests, probe and trace inside a protected block;
catch ordinary exceptions and store the failed stage, exception type/message and
traceback; in a finally block, attempt the post-run hash check and write a
REVIEW_FAILED receipt with finished_utc. An exception, post-check failure or
unavailable check must prohibit success and return nonzero. Write the receipt
through a temporary file and atomic replacement where possible. If the output
destination itself is unavailable, print the failure to stderr and exit nonzero;
do not promise receipt creation when the disk cannot be written. Preserve the
existing rule that an already-existing output directory is rejected unchanged.

Nonblocking improvements and coverage limits

The seven cases are sufficient for their narrow counterexample and controls;
they are not an exhaustive adversarial protocol suite. Additional v0.1 cases
could cover the reversed O/S direction, a forged SEND, wrong-route ACKs, ACKs
after receiver EXIT, and a structurally valid transported EXIT. For the EXIT
case, expect the actual existing route/actor rejection where applicable, rather
than invent a cryptographic rejection reason. Do not change the 20 original
tests. If extra cases are added, use new A identifiers and deliberately update
the runner's expected extension count and accompanying documentation.

Strengthen A06 with effect_applied == False and equality of the complete S VIEW
before and after rejection. Strengthen A02 with duplicate == True and equal
before/after VIEW for the second delivery. These are additional assertion guards;
the current expected outcomes are correct. In reproduce_unsigned_ack.py, capture
before_s_raw = [record.to_dict() for record in s.raw] before delivery and use that
at line 36 instead of a literal empty list. The literal is accurate in the current
fixture, but a measured snapshot is stronger evidence against fixture drift.

The README refers to an accompanying run receipt; the eight added files do not
include one or directly link the reported Windows receipts. Add an accessible
receipt/log link or label those as author-reported historical results. The fresh
Linux receipt included here provides independently reproducible current evidence
without rewriting those historical claims.

Demonstrated limitation versus proposed controls

Demonstrated: an attacker able to submit an Event and knowing the real local SEND
reference can supply a self-consistent S-labelled ACK that O accepts without S
participating. The public key_id label and event/content hashes are not proof of
S's authorization. S RAW is observer-visible fixture ground truth, not a claimed
production oracle available to O. This is a finite in-process counterexample;
it is not evidence of remote network reachability in a deployed system.

The October 19 independent integration note already documents exactly this
boundary and distinguishes it from the frozen artifact's declared acceptance
requirements. The PR faithfully preserves that distinction; no new discovery
priority or retroactive failure of the original acceptance record is established.

The authenticated-successor document is explicitly requirements only. Separate
endpoint private credentials, independently authenticated public-key provisioning,
signed canonical event/context, peer authorization, replay/session/epoch handling,
all-ingress enforcement and durable evidence are proposed and unimplemented.
Its F01-F12 rows are unexecuted future cases. The proposal also correctly states
that a valid signature alone cannot prove actual SEND receipt, honest execution,
local logging or Byzantine safety. A malicious holder of S's signing key can sign
a false ACK. No current test result validates those future controls. Implementing
authentication should remain a separate, versioned contribution.
